# CORE™ Test Selection Architecture
## Choosing the Evidence That Deserves to Be Generated
### Version 1.0

---

# 1. Purpose

This document defines how CORE™ decides **what test deserves to be run** for a particular strategic opportunity.

It deliberately does **not** prescribe a universal catalogue of tests.

A customer, market, technology, business model or manufacturing problem can require completely different forms of evidence.

Therefore:

> **CORE does not begin with a test type. CORE begins with a decision and an uncertainty.**

The architecture is designed to answer:

> **What evidence do we need, and what is the most credible way to generate it before making the decision?**

---

# 2. The Core Principle

> **Do not choose the test you know how to run. Choose the evidence that can answer the question that matters.**

The method must emerge from the uncertainty.

Therefore:

> **Uncertainty → Evidence Required → Method → Test → Learning → Decision**

not:

> **Favourite Test → Data → Rationalisation**

# 4. What Each Personality Contributes

## 4.1 Aditya Agarwal — Dynamic Problems

### Contribution

Problem framing.

The relevant lesson is:

> **The initial situation is not necessarily the correct problem statement.**

A situation may be framed differently depending on perspective and constraints.

### CORE use

Before designing a test, ask:

- What is actually happening?
- What is the initial problem statement?
- What assumptions are embedded in that framing?
- What changes if we alter the perspective?
- What changes if we alter the constraints?
- What is the problem worth solving?

### CORE output

> **Right Problem Frame**

# 5. Bonita Kolb — Research Question Discipline

## Contribution

Determining what information is actually required.

Kolb's relevant process is:

> **Identify assumptions → challenge them with evidence → generate better understanding of the actual problem/solution.**

Her research process also distinguishes between:

> **General Problem → Research Objective → Research Question**

and stresses that research should begin with a clear question rather than an unexamined assumption.

### CORE use

Ask:

- What do we already know?
- What evidence already exists?
- What are we assuming?
- What do we actually need to know?
- Who or what can provide that knowledge?
- What evidence would resolve the uncertainty?

### CORE output

> **Critical Question + Evidence Requirement**

# 7. Rita McGrath — Which Uncertainty First?

## Contribution

Prioritisation under uncertainty.

Not every unknown deserves immediate investigation.

The relevant discipline is:

> **Identify the assumptions/uncertainties that matter most to the decision and learn about those first.**

### CORE use

For each uncertainty assess:

### Consequence

If wrong, how badly does it affect the opportunity?

### Uncertainty

How little do we actually know?

### Decision relevance

Would resolving it change what we do?

### Learning value

How much could we learn relative to the effort?

The priority is not simply:

> “What is most uncertain?”

It is:

> **“Which uncertainty is most decision-relevant?”**

### CORE output

> **Critical Uncertainty**

---

# 8. Stefan Thomke — Experiment / Evidence Design

## Contribution

Choosing and designing an experiment that produces useful evidence for a decision.

The critical principle is:

> **An experiment should have a clear learning purpose before it is designed.**

Experimentation is not synonymous with:

- A/B testing
- landing pages
- prototypes
- surveys

Those are methods.

The appropriate method depends on what must be learned.

### CORE use

Ask:

- Can this uncertainty actually be tested?
- What evidence would discriminate between the alternatives?
- What is the most direct credible method?
- Is the test feasible?
- Will decision-makers accept the result?
- Will the result be reliable enough?
- Is the expected learning worth the effort?

### CORE output

> **Test Design**

# 9. CORE — Decision

CORE's role begins and ends with the decision.

The purpose of evidence is not:

> “We have conducted research.”

It is:

> **“We know enough to decide the next move.”**

Possible decisions include:

- **GO**
- **MODIFY**
- **STOP**
- **TEST AGAIN**
- **ESCALATE**
- **DEFER**

The exact decision vocabulary can vary by engagement.

# 11. Step 1 — Define the Decision

Do not begin with:

> “Let's test this idea.”

Begin with:

> **What decision are we trying to make?**

Examples:

- Should we pursue this customer segment?
- Should we build the product?
- Should we invest in the technology?
- Should we change the value proposition?
- Should we price it differently?
- Should we enter this market?
- Should we continue the pilot?
- Should we allocate additional capital?

# 12. Step 2 — Define the Problem Frame

Use the Dynamic Problems discipline.

Record:

### Situation

What is happening?

### Change

What has changed?

### Initial problem statement

What do we currently think the problem is?

### Alternative frames

What else could this situation mean?

### Constraints

Which constraints shape the problem?

### Desired outcome

What future state matters?

### Right problem frame

What problem are we actually trying to solve?

---

# 13. Step 3 — Identify the Decision Need

Translate the decision into an information need.

Example:

### Decision

> Should we commercialise the product for Tier-1 automotive suppliers?

### Weak research question

> Do automotive companies like our product?

### Better question

> What conditions determine whether Tier-1 suppliers would adopt this solution within their existing production environment?

### CORE principle

> **The question should be useful to the decision, not merely interesting.**

---

# 14. Step 4 — Inventory Existing Evidence

Before generating new evidence, ask:

> **What do we already know?**

## Internal evidence

Examples:

- sales records
- customer complaints
- service requests
- CRM data
- lost deals
- quotations
- production data
- financial records
- previous pilots
- customer support records
- internal expertise

## External secondary evidence

Examples:

- industry reports
- public filings
- government data
- competitor information
- technical literature
- market statistics
- customer publications
- regulatory information
- credible expert material

### Evidence quality questions

- Is it relevant?
- Is it credible?
- Is it timely?
- Is it accurate enough?
- Is it affordable to obtain?

### Decision

If existing evidence sufficiently resolves the question:

> **STOP RESEARCH. MAKE THE DECISION.**

New research is not automatically valuable.

---

# 15. Step 5 — Build WWHTBT

For the chosen strategic opportunity:

> **What would have to be true for this to succeed?**

Generate conditions across the relevant domains.

Do not force every domain into every engagement.

Potential domains:

- customer
- problem
- behaviour
- buying
- economics
- technology
- integration
- capability
- ecosystem
- regulation

---

# 16. Step 6 — Classify the Evidence Status

Every important assumption should be labelled:

### KNOWN

Supported by credible evidence.

### INDICATED

Some evidence exists, but it is incomplete.

### ASSUMED

Believed to be true without adequate evidence.

### UNKNOWN

There is insufficient information to form a meaningful conclusion.

This prevents the team from treating:

> **belief**

as:

> **fact**.

---

# 17. Step 7 — Find the Critical Uncertainty

Not every uncertainty deserves testing.

Score each important uncertainty on:

| Dimension | Question |
|---|---|
| Consequence | If false, how badly does it affect the strategy? |
| Uncertainty | How little evidence do we have? |
| Decision relevance | Would learning the answer change the decision? |
| Learning value | Can we learn something useful at reasonable effort? |
| Time sensitivity | Does the answer need to be known now? |

The priority should generally be:

> **High consequence + high uncertainty + high decision relevance**

not:

> **most interesting unknown**.

---

# 18. Step 8 — Determine the Evidence Required

Now ask:

> **What observation would actually reduce this uncertainty?**

This is the crucial bridge between strategy and test design.

Examples:

### Uncertainty

> Customers will pay.

### Evidence required

> Evidence of actual willingness to make a commercial commitment at or near the proposed price.

---

### Uncertainty

> Operators will adopt the workflow.

### Evidence required

> Observed behaviour in the real operating environment.

---

### Uncertainty

> Legacy machines can integrate.

### Evidence required

> Technical demonstration against representative equipment/data environment.

---

### Uncertainty

> The market is sufficiently attractive.

### Evidence required

> Credible evidence of target customers, reachable demand, competitive conditions and commercial economics.

---

# 19. Step 9 — Choose the Evidence Source

Possible evidence sources include:

## Existing evidence

Use when available.

## Internal experts

Use when organisational knowledge can answer the question.

## External experts

Use when specialist knowledge is required.

## Customers / buyers

Use when actual buyer behaviour or experience is required.

## Users / operators

Use when workflow or behaviour matters.

## Observation

Use when stated behaviour may differ from actual behaviour.

## Secondary research

Use when external facts or market conditions can be established.

## Commercial behaviour

Use when willingness-to-pay or commitment is central.

## Technical demonstration

Use when technical feasibility is the uncertainty.

## Controlled experiment

Use when alternatives can be tested under controlled conditions.

## Field test / pilot

Use when real-world system behaviour is necessary.

This is a **menu of evidence sources**, not a mandatory test taxonomy.

---

# 20. Step 10 — Select the Method

Only now choose the method.

The selection criteria are:

### Directness

Does it directly address the uncertainty?

### Credibility

Would the resulting evidence be believable?

### Behavioural proximity

Does it observe actual behaviour rather than hypothetical opinion?

### Speed

Can it produce useful learning within the decision timeframe?

### Cost

Is the effort proportionate to the decision?

### Feasibility

Can the test actually be executed?

### Reliability

Would the result be sufficiently robust for this decision?

### Decision utility

Will the result change what we do?

---

# 21. Step 11 — Determine the Evidence Standard

The evidence standard must be proportional to the decision.

There is no universal “valid sample size” or universal “proof threshold” for every CORE engagement.

Ask:

> **How strong does the evidence need to be before this particular decision can reasonably be made?**

Examples:

### Exploratory strategic question

Directional evidence may be sufficient.

### Product feature decision

Behavioural evidence may be sufficient.

### Major commercial commitment

Stronger evidence may be required.

### Large capital allocation

The evidence standard should be substantially higher.

### Safety-critical technical deployment

Technical validation must meet the relevant technical requirements.

The principle is:

> **Evidence standard follows decision consequence.**

# 23. Step 13 — Design for Discrimination

A useful test should help distinguish between competing possibilities.

Weak:

> “Ask customers whether they like the concept.”

Stronger:

> “Observe whether target buyers will take a concrete action under a defined condition.”

The question is:

> **What result would make us think differently?**

If no possible result would change the team's mind, the test is not serving a decision.

---

# 24. Step 14 — Run the Smallest Credible Test

The word is:

> **credible**

not:

> **smallest possible**.

The cheapest test is not automatically the best test.

A tiny test that cannot answer the question is wasteful.

Therefore:

> **Find the minimum level of evidence that can credibly discriminate between the relevant choices.**

This is where test design becomes a strategic capability rather than an experimentation gimmick.

---

# 25. Step 15 — Capture Evidence

Separate:

## Observation

What happened?

## Behaviour

What did the participant/customer/system actually do?

## Statement

What did they say?

## Interpretation

What might it mean?

## Inference

What are we now concluding?

## Confidence

How strong is the evidence?

## Contradiction

What does not fit our hypothesis?

This protects against confirmation bias.

---

# 26. Step 16 — Analyse Against the Decision

Do not ask only:

> “What did we learn?”

Ask:

> **“What did we learn that matters to the decision?”**

Use:

> Evidence → Pattern → Interpretation → Implication → Decision

For qualitative evidence:

> **Organize → Code → Concepts → Categories → Relationships → Interpretation → Recommendation**

AI can assist with organization, transcription, coding and comparison.

AI should not automatically become the final judge of strategic meaning.

---

# 27. Step 17 — Decide

The evidence must now lead somewhere.

Possible decisions:

### GO

Evidence is sufficient to proceed.

### MODIFY

The opportunity remains attractive but requires a change.

### STOP

A consequential condition failed.

### TEST AGAIN

The evidence is insufficient or ambiguous.

### ESCALATE

The evidence justifies a more serious test.

### DEFER

The opportunity may matter, but another priority deserves attention first.

---

# 28. Where “Guerrilla” and “Validity” Fit

These should **not** be mandatory test categories.

They are useful as **levels of evidence and commitment**.

## Guerrilla

A fast, inexpensive, directional learning move.

Purpose:

> **Find out whether the hypothesis deserves further attention.**

## Indicative

A stronger evidence-generation move.

Purpose:

> **Increase confidence sufficiently to justify the next level of commitment.**

## Validity

A more rigorous test appropriate to the consequence of the decision.

Purpose:

> **Generate evidence strong enough for the decision being considered.**

The exact method can vary at every level.

Therefore:

> **A customer interview can be guerrilla.**

> **A technical pilot can be guerrilla.**

> **A paid trial can be indicative.**

> **A structured field experiment can be validity-level.**

There is no universal mapping.

# 31. Test Selection Quality Gate

Before running a test, CORE should ask:

### 1. Is the decision clear?

If not:

> Stop.

### 2. Is the problem frame clear enough?

If not:

> Reframe.

### 3. Is the critical uncertainty identified?

If not:

> Return to WWHTBT.

### 4. Is existing evidence insufficient?

If not:

> Use existing evidence and decide.

### 5. Does the proposed evidence actually address the uncertainty?

If not:

> Redesign.

### 6. Is the method credible?

If not:

> Choose another method.

### 7. Would the result change the decision?

If not:

> Do not run the test.

### 8. Is the evidence standard appropriate to the decision?

If not:

> Adjust it.

### 9. Is the test feasible within the decision timeframe?

If not:

> Redesign or change the decision timeframe.

### 10. Is there a clear stop/decision rule?

If not:

> Do not run it yet.

# 34. What Should Remain Flexible

CORE should deliberately avoid prescribing:

- number of interviews
- exact sample size
- mandatory survey
- mandatory prototype
- mandatory landing page
- mandatory pilot
- mandatory A/B test
- mandatory customer interviews
- mandatory guerrilla test
- mandatory validity test

Those are **context-dependent methods**.

The architecture prescribes the **reasoning for selecting the method**, not the method itself.

---

# 35. Final Principle

> **The test is not the product. The decision is the product.**

The test exists to produce evidence.

The evidence exists to reduce consequential uncertainty.

The reduced uncertainty exists to improve the decision.

And the decision exists to determine the next action.

Therefore the complete CORE testing philosophy is:

> **Frame the right problem.**
>
> **Identify the decision.**
>
> **Determine what must be known.**
>
> **Use what is already known.**
>
> **Identify what would have to be true.**
>
> **Prioritize the uncertainty that matters.**
>
> **Choose the evidence that can actually resolve it.**
>
> **Design the most credible proportionate test.**
>
> **Let the evidence change the decision.**
