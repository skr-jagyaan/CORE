# CORE™ OS Architecture & Document Hierarchy v1.0

## 1. Purpose

This document defines the hierarchy between CORE's master operating systems, supporting modules, implementation specifications, registers and execution assets.

Its job is to prevent the CORE knowledge base from becoming a collection of competing source-of-truth documents.

It does not replace subject-specific architecture documents. It defines **where those documents sit and which level governs what**.

---

# 2. CORE MASTER ARCHITECTURE

CORE is organised around the transformation:

> **SIGNAL → IDEA → MARKET → ORGANISATION**

The commercial transformations are:

```text
₹499
SIGNAL → IDEA

₹39,999
IDEA → MARKET

₹5L
PRODUCT / BUSINESS → ORGANISATION
```

These are commercial transformations, not mandatory purchase stages.

The six master operating systems are:

```text
01  SOURCE OF TRUTH / MASTER ARCHITECTURE
02  GOLDEN THREAD / STRATEGIC THINKING
03  OFFER / CLIENT EXPERIENCE
04  CONTENT + PRE-SOLD ASSETS
05  DEMAND / VISIBILITY
06  DELIVERY + PROOF + LEARNING
```

A seventh operating system is **not** implied by this document.

The Master Integration OS is the integration/control layer connecting the six systems; it is not a seventh business function.

# 3. DOCUMENT HIERARCHY

CORE documents should be treated as five levels.

## LEVEL 1 — MASTER ARCHITECTURE

Defines a major operating system or the governance of the whole CORE system.

Examples:

- CORE Source of Truth / Document Register
- CORE Master Integration OS
- CORE Golden Thread / Strategic Thinking OS
- CORE Offer / Client Experience OS
- CORE Content + Pre-Sold Asset OS
- CORE Demand / Visibility OS
- CORE Delivery + Proof + Learning OS

These documents define **purpose, boundaries, major flows, principles and ownership**.

---

## LEVEL 2 — GOVERNING MODULE / DOMAIN ARCHITECTURE

Defines a major reusable system inside a master OS.

Examples include:

- Positioning Architecture
- Strategic Narrative
- Message House
- GTM / Funnel Architecture
- Evidence Selection Architecture
- LinkedIn ICP Demand Generation Architecture
- Golden Thread Management System
- Public Intellectual Engine
- Narrative Engine
- Conversation Engine
- Network Building Engine

These documents provide deeper domain logic without becoming competing master OSs.

---

## LEVEL 3 — IMPLEMENTATION SPECIFICATION

Defines how a system is actually built or delivered.

Examples include:

- 499 product system
- 39999 sprint architecture
- learner experience architecture
- learner workbook
- detailed session blueprint
- video production bible
- landing page system
- website architecture
- sales deck architecture
- dashboard specifications
- AI Personal Work OS specification

These documents should implement the governing architecture rather than redefine it.

---

## LEVEL 4 — REGISTER / CONTROL DOCUMENT

A register records the operating population of the system.

Current registers include:

- CORE Asset Register
- CORE Decision + Evidence Register
- CORE Automation Register
- CORE Source of Truth / Document Register

Registers answer questions such as:

- What exists?
- Where does it belong?
- What is its status?
- What is it linked to?
- What needs attention?

A register should not silently become the source of methodology.

---

## LEVEL 5 — EXECUTION ASSET / INSTANCE

These are individual outputs produced by the system.

Examples:

- LinkedIn posts
- YouTube videos
- newsletter issues
- podcast episodes
- executive briefs
- diagnostics
- cases
- decision autopsies
- client outputs
- tests
- evidence records
- testimonials
- campaign instances
- individual sales pages or emails

Execution assets should normally be traceable to a higher-level system or asset.

# 8. VERSION CONTROL RULE

When a conflict appears:

1. Check the relevant Master OS.
2. Check the governing domain architecture.
3. Check the implementation specification.
4. Check the register.
5. Treat execution assets as downstream unless explicitly elevated.

Do not solve contradictions by silently rewriting one document.

The conflict should be identified and the authoritative source explicitly updated.

---

# 9. SUPERSEDED DOCUMENTS

Older versions may remain in the Library for traceability.

They are not current merely because they still exist.

Examples of known version transitions include:

- older GTM versions superseded by GTM v5
- older Offer Architecture versions superseded by the current Offer Architecture
- older Positioning versions superseded by the current Positioning Architecture
- the original 3–5 opportunity sprint framing superseded for the primary commercial promise by the Idea → Market framing in the revised sprint architecture

Historical documents should be retained where useful, but should not be used operationally once superseded.

---

# 10. NEW DOCUMENT TEST

Before creating a new CORE document, ask:

### Is this a new operating system?

If yes, establish why it cannot live inside an existing master OS.

### Is this a reusable method or architecture?

It is probably a Level 2 module.

### Is this how something is built or delivered?

It is probably a Level 3 implementation specification.

### Is this tracking what exists or what happened?

It is probably a Level 4 register.

### Is this one actual output?

It is probably a Level 5 execution asset.

If none of these apply, a new document may not be necessary.

---

# 11. CORE DESIGN PRINCIPLE

The purpose of the document system is not to create more documentation.

It is to create a clear relationship between:

> **THINKING → SYSTEM → EXECUTION → EVIDENCE → LEARNING**

Every important CORE asset should have a place in that chain.

The architecture should become simpler as it matures, not more fragmented.
