# 1. Purpose

This document is the **source-of-truth register for the current CORE body of work**.

It answers four questions:

1. **Which document currently governs a subject?**
2. **Which documents are supporting rather than governing?**
3. **Which older versions are superseded?**
4. **Which documents should NOT be changed casually because they sit upstream of the system?**

This register is a **control document**.

It does not replace the underlying documents.

It tells us which underlying document to trust.

---

# 2. Status Vocabulary

## 🔒 CURRENT / AUTHORITATIVE

The latest document currently governing that subject.

Use this version when creating or revising downstream work.

---

## 🟢 ACTIVE SUPPORTING

The document is still useful and operationally relevant, but another document governs the higher-level decision.

It should not contradict the current authoritative document.

---

## 🟡 HISTORICAL / SUPERSEDED

An earlier version retained for traceability.

Do not use it as the primary source when a newer authoritative version exists.

---

## ⚪ SOURCE MATERIAL

Imported books, PDFs, prior research or external material that informed CORE.

Not a CORE governing document.

---

## 🔴 RETIRED

A document that should no longer be used operationally.

---

# 16. CURRENT vs HISTORICAL — CRITICAL RULE

A document's filename alone does not make it authoritative.

Authority comes from this register.

Where two current documents overlap:

1. use the higher-level governing document;
2. use the lower-level document for implementation detail;
3. do not silently reconcile contradictions;
4. escalate genuine contradiction into a new versioned decision.

---

# 17. CHANGE CONTROL

A current authoritative document should only be changed when:

### A. New evidence

Real evidence exposes a structural problem.

### B. Strategic decision

The business direction has intentionally changed.

### C. Architecture conflict

A validated downstream case exposes a contradiction.

### D. Production reality

A learner/customer beta reveals that the current design cannot work as intended.

Do **not** change a core document because:

- a new framework sounds interesting;
- another personality has a useful idea;
- a competitor uses different terminology;
- a new test method is discovered;
- a single anecdote feels persuasive.

---

# 18. VERSIONING RULE

Use:

> **MAJOR.MINOR**

### Major

Changes the governing logic.

Example:

> v1.0 → v2.0

### Minor

Refines implementation without changing the governing logic.

Example:

> v1.0 → v1.1

Examples already established:

> Evidence Selection Architecture v1.0 → v1.1

because the correction broadened the architecture from “test selection” toward evidence selection while preserving the underlying decision logic.
