# CORE™ ASSET REGISTER
## Version 1.0

## Status

**Operational register.**

This document inventories the current CORE asset families and their roles across the six master operating systems.

It does **not** replace source-of-truth documents. Where a subject-specific authoritative document exists, that document governs the substance. This register governs the **inventory, role, ownership and routing of assets**.

---

# 1. PURPOSE

The Asset Register answers five practical questions:

1. What assets does CORE currently have?
2. What job does each asset perform?
3. Which OS does it belong to?
4. Which audience state or commercial transformation does it support?
5. Is it a master asset, a supporting module, an implementation asset, a proof asset, or an execution asset?

The purpose is to prevent:

- duplicate creation;
- orphan assets;
- conflicting versions;
- unclear ownership;
- content that has no strategic role;
- assets that exist without a downstream routing path.

---

# 2. ASSET HIERARCHY

CORE assets should be understood in five levels.

```text
LEVEL 1 — MASTER ARCHITECTURE
The governing system or source of truth.

LEVEL 2 — OPERATING MODULE
A reusable framework, architecture or system inside a master OS.

LEVEL 3 — IMPLEMENTATION ASSET
A workbook, template, production specification, page, deck, automation or learner asset.

LEVEL 4 — PUBLIC / PRE-SOLD ASSET
An externally consumed intellectual, diagnostic or proof asset.

LEVEL 5 — EXECUTION INSTANCE
A specific post, video, episode, brief, client output, test, case or campaign produced from the system.
```

A Level 5 execution instance should normally be traceable to a higher-level asset or system.

# 17. ASSET CREATION GATE

Before creating an asset, answer:

```text
1. What audience state does this serve?
2. What belief or understanding should change?
3. Which CORE transformation does it support?
4. Which OS owns it?
5. Is there an existing asset that already performs this job?
6. Is this a master asset, module, implementation asset or execution instance?
7. What is the next logical asset or action?
8. What evidence or proof supports it?
9. Will the asset create reusable intelligence?
```

If these cannot be answered, do not create the asset yet.

---

# 18. VERSION CONTROL RULES

1. Do not create a new master asset when an existing master already owns the subject.
2. Update the authoritative source first when a strategic decision changes.
3. Mark downstream assets for review when their upstream source changes.
4. Retain superseded versions for traceability, but do not use them operationally.
5. Never let an execution asset silently redefine a master architecture.
6. Record new assets here before they become part of the production system.
